API Documentation

Enterprise-grade self-hosted REST API for dual HiTek (Phone) and ICMR (Aadhaar) SQLite databases with symmetric multi-hop BFS graph traversal.

Base URL

http://localhost:8000

Replace with your VPS IP or custom domain where the API is hosted (e.g., https://api.yourdomain.com).

All endpoints are documented interactively in Swagger UI at /docs. (ReDoc has been disabled per architecture spec).

Unified Lookup Endpoint

GET /api/lookup?q={phone_or_aadhaar}&depth={1-5}

Search by Indian mobile number or Aadhaar UID with symmetric multi-hop relational BFS traversal across all detected SQLite tables.

Query Parameters

Parameter Type Required Description
q string Yes* Unified search identifier. Auto-detects 10-digit mobile or 12-digit Aadhaar UID. Normalizes +91, 091, and leading 0.
mobile string Optional Explicit mobile phone search (strictly validates as 10-digit mobile). Cannot be combined with conflicting aadhaar.
aadhaar string Optional Explicit Aadhaar UID search (strictly validates as 12-digit Aadhaar). Cannot be combined with conflicting mobile.
number string Optional Legacy alias for q. Supports both 10-digit mobile numbers and 12-digit Aadhaar UIDs.
depth integer Optional Maximum BFS relational graph traversal hops (1 to 5, default: 3).

* Provide at least one identifier via q, mobile, aadhaar, or number.

Example Requests

GET /api/lookup?q=9876543210&depth=3
GET /api/lookup?aadhaar=123456789012&depth=2

Error Responses

Status Code Error Code Description
400 Bad Request MISSING_QUERY No search parameter was provided in the query string.
400 Bad Request INVALID_FORMAT Input format is not a valid 10-digit Indian mobile or 12-digit Aadhaar UID.
400 Bad Request CONFLICTING_PARAMETERS Both mobile and aadhaar parameters were passed with conflicting values.
401 Unauthorized UNAUTHORIZED API key required when API_AUTH_ENABLED=true. Provide via X-API-Key or Authorization: Bearer.
429 Too Many Requests RATE_LIMITED Client exceeded IP rate limit sliding window. Header Retry-After indicates wait time.
503 Service Unavailable DATABASE_UNAVAILABLE SQLite database engine is disconnected or undergoing maintenance.
500 Server Error DATABASE_ERROR Internal search query exception (detailed traces logged safely server-side).

Dedicated Phone Endpoint

GET /api/phone?number={10_digit_mobile}&depth={1-5}
GET /api/phone/{number}?depth={1-5}

First-class dedicated endpoint for mobile number queries. Automatically forces phone search mode, normalizes country prefixes (+91, 091, 0), and rejects non-phone inputs with 400 Bad Request.

Query & Path Parameters

Parameter In Required Description
number Path / Query Yes* 10-digit Indian mobile number (must begin with 6, 7, 8, or 9). Prefix formatting like +91 is stripped cleanly.
q Query Optional Alternative query parameter for number.
depth Query Optional Relational graph traversal depth (1 to 5, default: 3).

Example Requests

GET /api/phone?number=9876543210&depth=3
GET /api/phone/9876543210

Dedicated Aadhaar Endpoint

GET /api/aadhaar?uid={12_digit_aadhaar}&depth={1-5}
GET /api/aadhaar/{uid}?depth={1-5}

First-class dedicated endpoint for Aadhaar UID demographic lookups. Enforces strict 12-digit UID verification and traverses connected phone records across HiTek and ICMR tables.

Query & Path Parameters

Parameter In Required Description
uid Path / Query Yes* Strict 12-digit Aadhaar UID number (all non-digit delimiters like spaces or hyphens are stripped).
q Query Optional Alternative query parameter for uid.
depth Query Optional Relational graph traversal depth (1 to 5, default: 3).

Example Requests

GET /api/aadhaar?uid=123456789012&depth=2
GET /api/aadhaar/123456789012

Symmetric BFS Relational Traversal Engine

Unlike standard single-table lookup tools, the engine implements a bidirectional Breadth-First Search (BFS) graph traversal algorithm that bridges the gap between disparate data registries:

  • HiTek Telecom Tables: Phone-keyed records containing full names, father names, addresses, alternate contact numbers, and telecom circles.
  • ICMR Medical/Demographic Tables: Aadhaar UID-keyed records containing demographic profiles, states, districts, PIN codes, and linked phone numbers.

Visual Traversal Architecture

[ Hop 0: Input Seed ] ── (Phone: 9876543210 or Aadhaar: 123456789012)
          │
[ Hop 1: Primary Discovery ] ── Query HiTek & ICMR SQLite tables
          │                      Extract: Discovered Aadhaar UIDs & Phone Numbers
[ Hop 2: Cross-Registry Expansion ] ── Traverse cross-table relations (Phone ↔ Aadhaar)
          │
[ Hop 3: Multi-Hop Link Graph ] ── Deep transitive expansion across alternate numbers & linked family trees
          │
[ Canonical Deduplication ] ── Full identity profile merged with zero data loss

Configuring Traversal Depth

Depth Value Traversal Behavior Typical Latency Recommended Use Case
depth=1 Direct seed matches only. Exits before expanding newly discovered links. ~5-15 ms High-throughput batch verification or exact record checks.
depth=2 Follows 1st-degree relationships (Phone ↔ Aadhaar link). ~15-40 ms Standard intelligence correlation and demographic enrichment.
depth=3 (Default) Full 3-hop multi-link expansion across alternate phones and connected identities. ~30-80 ms Deep OSINT investigation, family tree tracing, and identity clustering.

Code Examples

1. cURL

# 1. Unified search by phone (auto-detects phone, depth=3)
curl "http://localhost:8000/api/lookup?q=9876543210&depth=3"

# 2. Dedicated Phone endpoint (path format, depth=2)
curl "http://localhost:8000/api/phone/9876543210?depth=2"

# 3. Dedicated Aadhaar endpoint (query param, depth=1 exact match)
curl "http://localhost:8000/api/aadhaar?uid=123456789012&depth=1"

# 4. Authenticated request (when API_AUTH_ENABLED=true)
curl -H "X-API-Key: your_secret_key" "http://localhost:8000/api/lookup?q=9876543210"

2. Python (requests / httpx)

import httpx

BASE_URL = "http://localhost:8000"

with httpx.Client(base_url=BASE_URL, timeout=10.0) as client:
    # Query dedicated phone endpoint with 3 traversal hops
    resp = client.get("/api/phone", params={"number": "9876543210", "depth": 3})
    data = resp.json()

    if data.get("found"):
        identity = data.get("identity", {})
        location = data.get("location", {})
        meta = data.get("meta", {})

        print(f"Target Located in {meta.get('response_time_ms')}ms across {meta.get('search_depth')} hop(s):")
        print("Names:", identity.get("names"))
        print("Primary Phones:", identity.get("primary_phones"))
        print("Aadhaar UIDs:", identity.get("aadhaar_numbers"))
        print("Districts:", location.get("districts"))
        print("Pincodes:", location.get("pincodes"))
    else:
        print("No records located.")

3. JavaScript / Node.js (fetch)

// Dedicated Aadhaar lookup with 2-hop cross-registry expansion
const uid = "123456789012";

  console.log("No matching target profile found.");
}

Self-Hosting Configuration

Configure the backend via environment variables or a .env file in the repository root:

Variable Default Description
DB_PATH /data/users.db Absolute path to your SQLite database file
API_HOST 0.0.0.0 Host bind address (use 127.0.0.1 behind Nginx reverse proxy)
API_PORT 8000 Listening port number
DEEP_SEARCH_DEPTH 3 Default BFS relational link hops (1 to 5)
MAX_RESULTS 25 Maximum rows retrieved per individual table query
MAX_GLOBAL_RESULTS 100 Global profile row ceiling across all tables in a single traversal
SQLITE_CACHE_SIZE_KB 64000 SQLite page cache in KB (~64 MB in RAM for sub-millisecond index hits)
SQLITE_MMAP_SIZE_BYTES 2147483648 SQLite memory-mapped I/O size (2 GB for zero-copy kernel page reads)
SQLITE_SYNCHRONOUS NORMAL WAL mode synchronization safety level (NORMAL optimizes throughput)
RATE_LIMIT_ENABLED true In-memory sliding-window rate limiting per client IP
RATE_LIMIT_REQUESTS 60 Maximum requests allowed per window
RATE_LIMIT_WINDOW_SECONDS 60 Sliding window duration in seconds
API_AUTH_ENABLED false Enable optional API key authentication
API_KEY "" Secret key checked against X-API-Key / Bearer

VPS Deployment & Performance Tuning

Unlike resource-constrained free tiers, a dedicated VPS (Ubuntu 22.04 / 24.04 LTS) unlocks the full throughput of SQLite with WAL mode, kernel-level mmap, and Uvicorn process management:

1. Systemd Service Unit

Create a dedicated systemd service file at /etc/systemd/system/osint-api.service:

[Unit]
Description=HiTek & ICMR OSINT Search Engine API
After=network.target

[Service]
User=www-data
Group=www-data
WorkingDirectory=/var/www/hitek-icmr-db-osint
Environment="PATH=/var/www/hitek-icmr-db-osint/venv/bin"
EnvironmentFile=/var/www/hitek-icmr-db-osint/.env
ExecStart=/var/www/hitek-icmr-db-osint/venv/bin/uvicorn api.main:app --host 127.0.0.1 --port 8000 --workers 4 --loop uvloop --http httptools
Restart=always
RestartSec=5
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now osint-api
sudo systemctl status osint-api

2. Nginx Reverse Proxy Configuration

Place this server block in /etc/nginx/sites-available/osint-api:

server {
    listen 80;
    server_name api.yourdomain.com;

    # Gzip Compression
    gzip on;
    gzip_types text/plain application/json application/javascript text/css;

    # Static Website Frontend
    location / {
        root /var/www/hitek-icmr-db-osint/website;
        index index.html;
        try_files $uri $uri/ /index.html;
    }

    # API Reverse Proxy
    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_buffering on;
        proxy_buffers 8 16k;
        proxy_buffer_size 32k;
    }

    # Health & Docs Endpoints
    location ~ ^/(health|docs|openapi.json) {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

3. SQLite Kernel & Hardware Tuning

  • Memory-Mapped I/O (PRAGMA mmap_size=2147483648): Maps 2 GB of the SQLite database directly into user space memory, eliminating read() system call overhead and context switches.
  • Write-Ahead Logging (PRAGMA journal_mode=WAL): Concurrent readers never block writers and writers never block readers.
  • Synchronous NORMAL (PRAGMA synchronous=NORMAL): Dramatically decreases fsync latency during transactions while maintaining full consistency in WAL mode.
